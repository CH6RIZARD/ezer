# Let code fly the dove; let footage flap it

**Use a transparent sprite sheet of an in-place flap cycle, moved along the designer's exact SVG path by a single Reanimated shared value.** Every other option either gives up path fidelity or alpha on one of the three platforms, or adds a native dependency that this repo avoids. The path is sampled once at build time into a small JSON array (about 500 × [x, y, angle], roughly 10–15 KB). On the UI thread, one `withTiming` progress value drives `translateX/translateY/rotate` and picks the sprite cell. The dove's anchor therefore sits on the drawn path in every frame and lands on the logo coordinate exactly, at every screen size. Realism then depends on the frames, not the runtime. The best source for those frames is a 3D rigged white dove rendered in Blender with a true alpha channel ($119-class asset, no matting halo). A $5 commercially licensed green-screen dove loop, chroma-keyed and despilled, is the faster but rougher alternative. AI video tools are the wrong place to put path control: none of them guarantees the path or the landing frame. Their only good use here is making the flap cycle. Lottie with photo frames runs to tens of MB. Rive needs a Nitro native dependency and has no stated web path. Alpha video has no Android-native path. Per-theme baked MP4s can work, but they turn a 1 MB asset problem into a colour-matching problem on three themes × three platforms.

## The deciding constraint is alpha on all three platforms with no new native code

Seven candidates were scored against this repo as it stands: Reanimated 4.1 and react-native-svg 15 installed, no expo-image, Lottie, Rive or Skia, and no committed `android/` folder.

| Method | Path fidelity | Realism | Size | Startup | Alpha on iOS / Android / web | New native dep | Effort (1 dev) |
|---|---|---|---|---|---|---|---|
| **Sprite sheet + Reanimated on precomputed path** | Exact (same `d` string) | As good as the frames | ~0.3–1.5 MB sheet + ~10 KB JSON | One texture, UI-thread transforms | Full 8-bit PNG/WebP everywhere | None | ~150 lines + asset work |
| Lottie (raster frames) | Exact only if the AE path is rebuilt to match | Good | Tens of MB for photo sequences | Decodes many bitmaps at mount | Yes, but web needs an extra player | lottie-react-native 7.3.x | AE/bodymovin pipeline |
| Rive (mesh-deformed photo + Follow Path) | Exact only if the path is rebuilt in Rive | Very good, smooth at any fps | Small (one image) | Native renderer | Web not stated for the new runtime | Nitro + Rive, dev build | Learn the Rive editor |
| Per-theme baked MP4 (Remotion/ffmpeg) | Exact at render time; fixed to one aspect ratio | Depends on the sprite or 3D render | ~0.4–1.5 MB × 3 themes | Player startup, first-frame flash risk | n/a (background baked in) | None (expo-video) | Remotion half-day + colour calibration |
| Alpha video (HEVC alpha / WebM alpha) | Exact at render time | Same | Small | Player startup | **Android renders alpha as black** | Shader/Skia needed for Android | High |
| AI video with motion paths | Soft, a few px average error at 480p, no guaranteed endpoint | Potentially high, but wordmark warps | Baked video | Player | Baked | None | Unpredictable re-rolls |
| Skia Atlas sprite | Exact | Same frames | Same as sprite sheet | Best (one GPU draw) | Web needs CanvasKit WASM | Skia | Upgrade path only |

The Lottie problem is file size. Raster sequences are embedded as base64 in the JSON. Real reports put a 1000×900 PNG sequence at about 86 MB, and a compressed JPEG sequence at about 30 MB ([LottieFiles](https://help.lottiefiles.com/image-handling-best-practices-); [Webflow forum](https://discourse.webflow.com/t/lottie-animation-from-a-rendered-sequence-keeping-file-sizes-small/179687)). On SDK 54 it also adds a native dependency pinned to 7.3.x, and web needs a separate `@lottiefiles/dotlottie-react` package ([lottie-react-native](https://github.com/lottie-react-native/lottie-react-native)). Rive is the most attractive on realism: one photo, wings deformed by a bone-driven mesh ([Rive meshes](https://rive.app/docs/editor/manipulating-shapes/meshes)), and a Follow Path constraint with Orient ([Rive Follow Path](https://rive.app/docs/editor/constraints/follow-path-constraint)). But its current React Native runtime is built on Nitro and needs `react-native-nitro-modules`, its docs don't mention web, and the older package is in maintenance ([Rive RN docs](https://rive.app/docs/runtimes/react-native/react-native); [rive-react-native](https://github.com/rive-app/rive-react-native)). Both Lottie and Rive also make the designer's tool a second source of truth for the path, so "exact" depends on someone redrawing the curve by hand.

Animated WebP through core `Image` is ruled out. Expo's SDK 54 template ships `expo.webp.animated=false` ("~3.4 MB increase", "iOS doesn't support animated webp") ([Expo template gradle.properties](https://raw.githubusercontent.com/expo/expo/sdk-54/templates/expo-template-bare-minimum/android/gradle.properties)). Even where it plays, its frame clock can't be synced to path progress.

## Video routes fail on alpha or on colour, not on motion

Transparent video splits by platform. HEVC-with-alpha plays on Apple platforms, VP9 WebM alpha plays in Chrome, Firefox and Edge, and Safari doesn't support WebM transparency ([CSS-Tricks](https://css-tricks.com/?p=328311); [hontran.dev](https://www.hontran.dev/blog/transparent-video-web-hevc-alpha-ffmpeg)). On Android, ExoPlayer "does not support alpha channel videos" and a transparent WebM "will be rendered as black". The workaround is a stacked colour-plus-matte video composited in a shader, and that is Android-only ([expo-transparent-video README](https://unpkg.com/expo-transparent-video@0.3.3/README.md)). Producing HEVC alpha also needs `hevc_videotoolbox`, which runs only on macOS, and this developer has no Mac ([hontran.dev](https://www.hontran.dev/blog/transparent-video-web-hevc-alpha-ffmpeg)). The only alpha-video answer that covers all three platforms is a Skia or GL shader, which is a new native dependency.

Per-theme baked MP4s avoid alpha by drawing the background into the video. That works mechanically: expo-video plays a `require()`'d asset and exposes `onFirstFrameRender` for hiding a cover image ([Expo docs, expo-video v54](https://docs.expo.dev/versions/v54.0.0/sdk/video/)). The cost moves to colour. H.264 colours "will never match perfectly" against CSS/RGB hex values and render differently across devices ([Adobe community](https://community.adobe.com/t5/after-effects-discussions/exporting-h-264-colours-don-t-match-rgb-hex/td-p/11204260)). An sRGB source without transfer tags comes out washed out in Firefox ([Mozilla bug 1783458](https://bugzilla.mozilla.org/show_bug.cgi?id=1783458)), and Safari and Firefox disagree on which `color_trc` tag is right ([ASWF FFMPEG defaults](https://wiki.aswf.io/download/attachments/16031068/FFMPEG%20defaults.pdf?api=v2)). The cream #F7F3EA sits near the top of limited range and is the hardest of the three themes to match; #000000 is trivially safe. On the web, iOS Low Power Mode blocks even muted autoplay ([WebKit bug 219889](https://bugs.webkit.org/show_bug.cgi?id=219889)). A video also fixes the composition to one aspect ratio, so the dove's landing point drifts from the live logo on any screen that `cover` crops differently. The sprite approach has none of these problems: the background is the real themed View, and the landing coordinate is computed from the same layout as the logo.

Remotion stays useful for one job: previewing and rendering the flight offline. `@remotion/paths` `getPointAtLength` has no dependencies and works without Remotion ([Remotion paths](https://remotion.dev/docs/paths/)). The same module can generate the app's sample JSON, and it can also render a marketing clip later.

## AI tools can generate a convincing wingbeat, but they can't land a bird on a pixel

Every trajectory-controlled generator treats the path as a soft condition. Kling's Motion Brush says the element is "expected" at the path endpoint, not that it will be there, and paths are drawn by hand in the UI ([Kling quickstart](https://kling.ai/quickstart/how-to-animate-image-parts)). The best open model, Wan-Move, accepts per-frame pixel coordinates but reports an average endpoint error of **2.6 on MoveBench at 832×480**. Its stated failure modes include occlusion and implausible motion, both of which a dove circling a wordmark produces ([Wan-Move](https://arxiv.org/html/2512.08765v1)). ByteDance's ATI lands only **34.7% of tracked points within about 10 px**, and fails on very fast motion ([ATI](https://arxiv.org/html/2505.22944)). These models also generate the whole frame, so the wordmark would be redrawn by the model and could warp. The output is a fixed 5 s, 480p clip rather than an overlay on live UI. Licensing matters if AI frames are used at all. Runway says outputs carry no non-commercial restriction ([Runway help](https://help.runwayml.com/hc/en-us/articles/21668707517587)). Kling's free tier is reported as non-commercial ([Atlas Cloud](https://www.atlascloud.ai/blog/guides/kling-ai-pricing)).

AI's legitimate role is upstream: a static-camera, in-place flap clip whose position is then owned by code. For that job, stock and 3D are cheaper and cleaner. UltraKey sells a looped, in-place white dove on green screen, with a commercial licence at $5 ([UltraKey](https://ultrakey.gumroad.com/l/flyingdove)). Rigged, animated white doves with fly and glide loops sell for $119 ([Superhive](https://superhivemarket.com/products/realistic-animated-white-dove-3d-model)), with another listing that includes takeoff and turns ([Fab](https://www.fab.com/listings/561131e4-f9d4-4992-981d-76037eb79f92)).

## Producing a clean, loopable, matted flap cycle

The 3D route gives the cleanest result because it skips matting entirely. Open the rigged dove in Blender, lock the camera, and play the fly loop in place. Render with Film > Transparent to a PNG sequence, which gives true soft alpha on feather edges with no background to bleed in. Render two extra things: four to eight landing frames (wings flaring forward to brake, then folding), and one perched frame that matches the logo dove's silhouette. If the drawn path sends the bird in both directions, also consider rendering the cycle from two or three headings, because the next section's mirroring trick only covers left versus right. This is a judgement, not a sourced figure.

For the footage route (UltraKey or AI), the background choice decides the quality of the matte. A white dove on white shares luminance with the background, so any matte either erodes the feather edges or leaves a light halo. Over the purple and black themes, that halo is plainly visible. Use the green-screen source, or prompt an AI tool for a flat mid-grey or chroma-green background with a locked camera; Kling's Static Brush stops camera creep ([Kling quickstart](https://kling.ai/quickstart/how-to-animate-image-parts)). Key it with chroma key plus despill, which is deterministic and doesn't flicker. Where the key fails on ambiguous edges, use a soft-alpha matting model. MatAnyone's authors report that RVM struggles on ambiguous backgrounds ([MatAnyone](https://arxiv.org/html/2501.14677v1)), and MatAnyone 2 targets the hard, segmentation-like edges of v1 ([MatAnyone 2](https://arxiv.org/pdf/2512.11782)). A hard mask always halos on a new background ([RunComfy](https://www.runcomfy.com/comfyui-nodes/TrentNodes/mat-anyone-matte)).

To make the loop, don't trust "start frame = end frame" generation alone. Take three to five seconds of steady flapping. Use frame differencing to find two frames where the wings are at the top of the upstroke, then cut exactly one or two whole wingbeats between them. Crossfade two or three frames at the seam if needed. After matting, re-centre each frame on the bird's centroid, so drift baked into the footage doesn't fight the code-driven motion. Choke the matte by 1 px and export premultiplied alpha. Those last steps are reasoned rather than sourced.

Pack the result into one sheet:

- **Layout:** 12 flap frames plus 4–8 landing frames, in cells about twice the on-screen size (256×256 px cells for a ~120 dp bird).
- **Sheet size:** one 1024×1024 or 1024×1536 PNG/WebP, about 4–6 MB decoded.
- **Why that size:** Android rejects bitmaps larger than the GPU's `GL_MAX_TEXTURE_SIZE`, which is 4096 on older devices ([AOSP hwui](https://android.googlesource.com/platform/frameworks/base/+/e927ec0/libs/hwui/TextureCache.cpp); [TIMOB-27471](https://jira-archive.titaniumsdk.com/TIMOB-27471)), so staying at or under 2048 leaves headroom.

The cream theme is the one place a white dove can wash out. One sheet works on all three backgrounds if the bird carries its own soft grey shading. If the light theme still looks flat on device, ship a second sheet for light mode with a faint contact shadow, rather than pursuing full per-theme video.

## Implementation steps in this repo

First, export the designer's path as an SVG `d` string in the same viewBox as the EZER wordmark. Then write a Node script, committed under `scripts/` and using `@remotion/paths` or the browser's `getPointAtLength`, that resamples the path to about 500 points at equal arc length. The script computes `angle = atan2(dy, dx)` between neighbours, unwraps jumps larger than π so the bird never spins 360°, smooths the angle with a short moving average, and writes the result to JSON. Resampling by arc length keeps the speed even, because equal Bezier `t` steps bunch up near control points. Easing is applied to the progress value, not to the geometry. Sampling at runtime with react-native-svg's `getPointAtLength` is unverified on native, so the build-time JSON is the safer choice.

In the loading-screen component, scale the samples with the same `screenWidth / viewBoxWidth` factor that lays out the wordmark. Mount one `overflow: 'hidden'` View the size of one cell. Inside it, put one `Image` the size of the whole sheet, offset by `-col*cellW, -row*cellH`. A `useAnimatedStyle` worklet then reads `progress` and does three things:

- **Position and heading:** lerps between samples `floor(i)` and `ceil(i)` for translate and rotate.
- **Wing frame:** picks the cell from `floor(progress * flaps * 12) % 12`, switching to the landing frames over the last ~10% of the path.
- **Direction:** mirrors with `scaleX: -1` and rotates by `angle − π` whenever the heading points leftward, so a side-view sprite never flies upside down.

The mirroring step is an inference from how the sprites are drawn, not from a source.

Run a single `withTiming(1, { duration: ~3500, easing: motion.easeOut })` on mount. The completion callback hands off through `scheduleOnRN` once, crossfading the sprite into the static logo dove at the identical coordinate. Do not attach listeners to the value, per the repo's rules in CLAUDE.md. Under `useReduceMotion()`, skip the flight and fade in the landed dove. Never make the app wait for the animation: if loading finishes first, jump `progress` to 1. Reanimated runs this in plain JavaScript on the web, which is fine for one transform ([Reanimated web support](https://docs.swmansion.com/react-native-reanimated/docs/guides/web-support/)). Check it on the S22 with `gfxinfo`, as with SpinCard. If it ever stutters, Skia's Atlas is the drop-in upgrade, at the cost of one native dependency.

## Conclusion

The question "which animation tool" hides two separate problems with opposite solutions: where the bird is, and what its wings look like. Position needs determinism and responsiveness, which only live code gives. Appearance needs photographic detail, which only rendered or filmed frames give. Every all-in-one option (Lottie, Rive, MP4, AI video) forces a compromise on one problem to solve the other, and pays for it in megabytes, native dependencies, colour drift or a missed landing.

Splitting the two problems also makes the work incremental. Ship with the $5 keyed loop this week. If the wings read as flat, swap in a Blender-rendered sheet later without touching a line of motion code. Two things remain unmeasured: decode time of the sheet on a low-end Android, and whether a single side-view sprite reads convincingly on the tightest curves of the path. Test both on device before investing in a multi-heading 3D render.
